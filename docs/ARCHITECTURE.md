# Архитектура проекта (Python Bot Edition)

Проект построен по принципам модульной архитектуры, адаптированной для экосистемы Python. Мы сохраняем строгое разделение ответственности, обеспечивая чистоту бизнес-логики и типизацию через `mypy`.

## ⚛️ Ядро (The Core Kernel)

Ядро структурировано по технологическим доменам. Это предотвращает «загрязнение» логики сетевыми API или зависимостями фреймворков.

### Структура `core/`:

1.  **`core/primitives/`** (Universal)
    - **Что это:** Чистые функции, обработка строк, математика, логика маппинга данных.
    - **Зависимости:** 0. Никакого Discord.py или OpenAI API.
    - **Цель:** Легкая тестируемость.

2.  **`core/integrations/`** (Adapters)
    - **Что это:** Обёртки над внешними сервисами (OpenAI, OpenRouter, Discord Gateway).
    - **Цель:** Изоляция внешней нестабильности. Если API изменится, мы меняем код только здесь.

3.  **`core/resilience/`** (Resilience & Retry Policy)
    - **Что это:** Модуль отказоустойчивости, содержащий [`RetryPolicy`](src/core/resilience/policy.py:6) и прокси-провайдер [`RetryingLLMProvider`](src/core/resilience/proxy.py:16).
    - **Цель:** Прозрачное оборачивание любых `BaseLLMProvider` с экспоненциальной задержкой и защитой фазы рукопожатия при стриминге (Stream Handshake Guard).

4.  **`core/types/`** (Domain Contracts)
    - **Что это:** Pydantic-модели и TypedDicts, описывающие структуру данных бота.
    - **Цель:** Обеспечить строгую типизацию данных, передаваемых между модулями.

## 🏗 Принципы слоев (Boundaries)

Мы используем `mypy` в режиме `--strict` для защиты границ.

### 1. Feature Layer & Vertical Slice Architecture ([`src/features/`](src/features/))

- **Назначение:** Реализация возможностей бота на основе **Vertical Slice Architecture (VSA)**. Каждая фича в [`src/features/`](src/features/) (например, [`discord_bot`](src/features/discord_bot/), [`telegram_bot`](src/features/telegram_bot/), [`admin_panel`](src/features/admin_panel/)) представляет собой вертикальный срез (vertical slice), инкапсулирующий всю необходимую логику для конкретного бизнес-процесса или интерфейса взаимодействия (клиенты, обработчики, мессенджеры, галды/ограничения и шаблоны).
- **Структура:** Автономные подпапки в [`src/features/`](src/features/), объединяющие специфичные для фичи компоненты.
- **Правила:**
  - Срезы могут использовать общие модули [`src/core/`](src/core/) и [`src/lib/`](src/lib/).
  - Запрещено напрямую вызывать внешние API в обход [`src/core/integrations/`](src/core/integrations/).

### 2. Domain Logic (`lib/`)

- **Назначение:** Основная логика обработки данных.
- **Пример:** [`lib/context_builder.py`](src/lib/context_builder.py:1) (сбор истории), [`lib/token_calculator.py`](src/lib/token_calculator.py:1).
- **Правила:** Могут использовать `core/primitives/`. **Запрещено** использование JSX (по понятным причинам) и сторонних UI-библиотек.

## 🧠 Принципы проектирования (Design Principles)

### 1. Mining & Refining (Добыча и Обогащение)

Принцип разработки остается неизменным:

1.  **Mining (Exploration):** Быстрая реализация функции в [`main.py`](src/main.py:1) или отдельном скрипте.
2.  **Refining (Exploitation):** Перенос логики в изолированные функции/классы в `lib/` или `core/`, покрытие их тестами (`pytest`).

### 2. Dependency Flow (Гравитация зависимостей)

Поток данных:
`bot.py` (Entry Point) → `features/` → `lib/` → `core/`

- `bot.py` — это только клей (glue code). В нем не должно быть сложной бизнес-логики.
- `lib/` — чистая логика (парсинг истории, расчет токенов).
- `core/` — инфраструктура.

### 3. Type Integrity (Целостность типов)

В Python мы используем `Pydantic` для рантайм-валидации и `mypy` для статической.

- **No Any-Type Policy:** Использование `Any` запрещено, за исключением случаев на границе с внешним API (например, при парсинге JSON), сразу после этого данные должны конвертироваться в `BaseModel`.
- **Type Guards:** Используем функции `isinstance()` и Pydantic `model_validate()`.

### 4. Stream Handshake Guard (Защита фазы рукопожатия стриминга)

При работе с потоковыми ответами (`AsyncGenerator`) логика повторов через [`RetryingLLMProvider`](src/core/resilience/proxy.py:16) обязана защищать **только фазу подключения и получения первого токена** (`anext`). Повторный запуск генератора после получения части ответа приведёт к дублированию текста у клиента.

## 🛡 Качество кода

- **Strict Mypy:** Все функции должны иметь аннотации типов (`def func(arg: int) -> str:`).
- **Ruff:** Стандарт для линтинга и сортировки импортов. Автоматически исправляет структуру импортов (аналог `simple-import-sort`).
- **Dependencies:** Все зависимости управляются через `pyproject.toml` (через `uv` или `pip`).
